# 1.4：按用途归并与显式迁移

先升级 WEBUI.for.SingBox 至 **1.4.0 或更新版本**。插件中心只获取元数据，点击安装/更新才下载所选 JS；不会自动安装、迁移、卸载或运行插件。本轮目录只有 **14 个插件**，六个旧包已从仓库删除，插件中心不再提供兼容区或旧包下载。主程序不打包脚本。

| 旧 ID | 当前能力 | 手动迁移参数 |
| --- | --- | --- |
| `plugin-index-the-proxy-name` | `plugin-subscription-organizer` 订阅节点整理 | `RenameMode: "index"` |
| `plugin-modify-proxy-name` | 同上 | `RenameMode: "flags"`，原四个参数原名复制 |
| `plugin-beautiful-node-name` | 同上 | `RenameMode: "beautify"`，原五个参数原名复制 |
| `plugin-duplicate-proxies-removal` | 同上 | `RemoveDuplicates: true`，可与一个命名模式组合 |
| `plugin-network-info` | `plugin-network-diagnostics` 网络诊断 | 复制 `Route`、`Sites`，`CheckExit: true` |
| `plugin-geoip-search` | 同上 | 复制 `Route`、`IP`，`LookupIP: true`；不需要出口查询可设 `CheckExit: false` |

主程序过滤已缓存目录中的旧包，旧 ID 的安装和更新请求也会拒绝。用户设备上已经安装的源码、参数与启停状态保持原样，不会自动删除或替换。新插件保留对旧 ID 的互斥声明，即使历史脚本没有反向声明，也不能同时启用。若加载历史数据时已有冲突，执行会明确失败，不会静默双运行。需要继续使用旧脚本时应自行保留备份；本仓库不再发行更新。

建议迁移顺序：

1. 导出旧源码和参数，记录当前订阅缓存或使用测试订阅。
2. 将要替换的旧插件在插件页**禁用**；不要求删除，便于回退。
3. 手动安装当前插件。订阅整理的 `Enabled` 默认为 `false`，不会立刻改名或过滤。
4. 复制上表对应参数，检查命名模式、去重与筛选开关，再启用 `Enabled`。三个旧命名策略只能选择一个，不应串联。
5. 更新测试订阅或手动运行缓存订阅，检查节点与配置引用，再决定是否用于其余订阅；脚本不会重启核心。
6. 回退时先在插件页禁用新插件，再启用旧插件。只关闭新插件内部 `Enabled` 仍不等于插件页禁用，互斥检查依然生效。

订阅整理按“筛选 → 去重 → 单一命名”执行，默认各项都不启用。名称筛选只使用插件自己的正则，不重复运行订阅元数据中的 `include`、`exclude` 或协议过滤。协议数组匹配节点的精确 `type`，例如 `shadowsocks`、`vmess`。订阅结构分组和流量/到期提示保留；组成员随被过滤节点移除，默认成员被过滤时改为剩余第一个成员。全部可用节点被过滤、组变空、保留节点依赖被删除的 `detour` 或同名节点产生不明确引用时，整个操作失败并保留旧缓存。

去重比较除名称和 GUI 身份外的完整连接配置，保留凭据、TLS、协议、`detour` 不同的节点。旧名称不明确对应多个连接时保守保留；不会猜测引用应指向哪个连接。命名保留 142 地区/907 关键词及旧选项。单独命名、协议筛选与去重有重复执行回归；名称正则作用于本次输入名称，已改名缓存再次手动运行前应检查正则是否仍适用，不能假设任意“正则筛选 + 改名”组合具有幂等性。

## TUN 中旧客户端规则的迁移

透明代理插件继续负责 TUN 入站、接口、排除网段、可选 DNS 劫持与该 TUN 默认出口；**不再在表单中推广 `ClientRules`**。旧参数仍会读取，不静默删除。客户端策略属于独立的 `plugin-client-policy`，可用于已有 TUN、普通入站或端点。

1. 将旧 `ClientRules` 数组复制到客户端策略的 `Rules`。
2. 给每条规则添加旧 TUN 标签，例如 `"inbound": ["router-tun"]`，保留原来只匹配该 TUN 的范围。
3. 在旧 TUN 插件高级 JSON 中显式设 `"ClientRules": []` 或删除该字段，然后启用新客户端策略。
4. 预览生成配置，确认 DNS 劫持仍在客户端路由之前，目的标签存在，管理设备仍能访问。保存后按需手动重启核心。

新的客户端策略遇到已有来源 CIDR 重叠的终结规则会拒绝生成；TUN 兼容参数也作反向检查，因此两种插件顺序都不会静默覆盖。检查包含 IPv4/IPv6 和嵌套规则；来源条件自身或祖先带 `invert` 时不猜测补集，保守拒绝。即使目的端口或入站不同，也要求先整理重叠来源策略。完全相同的生成规则可重复生成而不追加。

**创建 TUN 的插件应放在客户端策略之前**，这样新策略能引用其实际标签，并位于 TUN 默认出口之前。TUN 后运行且设置 `DefaultOutbound`、已有来源策略时会明确报错，避免默认出口遮挡设备规则。TUN 与客户端策略都保留现有 DNS/sniff/resolve 等前置步骤；如果这些步骤前夹着终结路由，应先在配置页整理顺序，插件不会猜测重排。不会自动清理用户规则、修改防火墙或连接真实路由器验证。

## 新增策略与现有插件分工

- DNS 分流只为匹配条件选择**已有解析器**；Hosts 继续提供 hosts 数据，AdGuardHome 继续对接已有服务，TUN 继续处理 DNS 流量截获。
- 客户端分流只为明确来源生成 route/reject 规则；TUN/监听插件创建入口，规则集插件创建引用，出站链插件处理 dial detour，URLTest 负责候选组。
- 通用配置覆盖保留为高级操作；若同时覆盖这些专用生成器写入的字段，应检查插件顺序与最终配置，不把多套相同规则同时启用。

所有验证使用测试数据、本机进程或独立模拟环境；未访问真实 GL-MT3600BE。模拟测试不能证明某台实体固件的 TUN、防火墙和 DNS 设置正确。
